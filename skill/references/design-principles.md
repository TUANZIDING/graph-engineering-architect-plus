# 设计原则与故障手册

本文件说明 geaplus 每条检查背后的理由，供 design / diagnose / repair 时查阅。

## 1. 为什么单个回路会出事

一个回路只看得见自己的指标，所以有四种它自己发现不了的毛病：

| 毛病 | 回路内部为什么看不见 | 图层面的解法 | geaplus 检查 |
|---|---|---|---|
| 钻指标空子 | 它只拿指标当“好”的定义 | 给指标配反指标 + 现实锚点 | E-GOODHART、E-NOCOUNTER |
| 看不见目标本身是否对 | 回路不能评价自己的参考值 | 目标修订交给更慢、由人管的回路 | E-METACAPTURE |
| 与别的回路打架 | 各自优化的变量互相影响 | 冲突前就写好仲裁人与优先级 | E-ARBITER、W-PRIORITY |
| 测量慢慢失真 | 数据源、口径、管道会漂 | 锚点要有有效期，审计回路独立查来源 | decayed_measurement |

## 2. 一张“扎根”的图至少要有什么

- 人拥有的根结果，写清可观察的成功标准和排除项；
- 至少一个执行回路，一个独立验证回路；
- 一个反指标或审计回路（专门找“便宜的胜利”）；
- 目标会冲突时，一个仲裁或治理职责；
- 至少一个冻结的现实锚点；
- 改目标、改锚点、扩权限、改冻结规则，都要过人工门；
- 停止、回滚、升级、交接都有去处。

这些是职责，不是人头。一个确定性脚本、一位医生、一个模型都可以承担一个节点。

## 3. 怎样算一个好锚点

自查五问：
1. 它量的是真实结果，还是方便拿到的代理？
2. 证据是真的执行/观察出来的，还是转述的？
3. 来源和被优化的回路无关吗？
4. 被优化的回路能不能改它、藏它、重新定义它？
5. 什么时候过期？过期后谁有权废弃或替换？

常见的“假独立”：训练回路能偷看的留出集；读同一张坏表的第二个看板；数据和评分逻辑都共享的第二个模型。

## 4. 反指标怎么配

反指标用来拆穿“便宜的胜利”，不是堆一排同等重要的数字。仲裁仍然要写优先级。示例：

- 信号数量 ↔ 阴性对照的假阳性率、复算一致性
- 病历完整率 ↔ 与原始记录一致率、模板化痕迹
- 模型分数 ↔ 校准、亚组误差、分布漂移
- 稿件推进速度 ↔ 结论与证据是否匹配、可复现性
- 降本 ↔ 可靠性、安全、隐藏的人工

## 5. 快慢分层

| 层 | 节奏 | 能做什么 |
|---|---|---|
| 执行 | 每次迭代 | 在冻结边界内动作 |
| 验证 | 每个候选 / 每版 | 判这一版能不能过 |
| 审计 | 每周 / 每月 | 查来源、口径、漂移 |
| 治理 | 每季度 | 审目标、阈值、取舍 |
| 人 | 需要时 | 改根目的、冻结规则、权限 |

快层反复改慢层的变量，会振荡、掩盖因果、让故障无从定位（E-CADENCE）。

## 6. 典型故障与修法

| 故障 | 信号 | 修法 |
|---|---|---|
| 装饰图 | 箭头多，没有一条能约束、否决或升级 | 合并重复节点，每条边写清权力和 artifact |
| 共享来源互证 | 执行、验证、审计都读同一管道的派生报告 | 加独立来源或直接执行的锚点，写有效期 |
| 元回路劫持 | 改进者能降阈值、改测试、改成功定义、拆门 | 冻结这些控制项，改动只能提议，经人工门 |
| 局部成功、全局受损 | 每个节点都达标，根结果没人复核 | 系统级结果检查去约束最终人工门 |
| 节奏搅动 | 快反馈频繁改长期策略或评估口径 | 分层，慢变量设最短观察窗 |
| 看守剧场 | 验证者只复述执行者的报告或样本 | 写明独立的取证、抽样和失败信号 |
| 共识即完成 | 大家都同意就宣布成功 | 要求锚点通过、确定性检查、终态交接 |

## 7. 修复顺序

一次只动一层，从下往上：根结果与归属 → 现实锚点与来源 → 验证者独立性 → 边的权力与仲裁 → 节奏分离 → 节点实现。结构有病时，先修扎根和权力，再考虑加 Agent 或重试。
